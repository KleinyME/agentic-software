# Shared Agent Workspace

## Choose context by the job

Keep one owner-facing partner when the owner wants continuity across personal and business work. A business lead coordinates one business; specialists receive bounded assignments. Executive responsibilities do not require permanent executive bots. Preserve independent verification when a task needs it.

Map each conversation to its runtime profile, accountable role, permitted knowledge scopes, current project, and return destination. Messaging topics separate transcripts; they do not by themselves restrict external memory, shared MCP tools, filesystem access, or credentials.

Start with the current project, then follow relevant dependencies. A task involving an agent's memory can legitimately span the business application, runtime, memory service, and shared skill suite. Permit that expansion within authorized scopes; do not inject unrelated personal context. Distinguish the ability to access a source from the decision to load it.

## Mission Control and owner-wide work

When Mission Control is installed, use its existing workspace/project model for personal life, businesses, and other work. A workspace is an area of responsibility, not necessarily a company. Personal projects can cover travel, home, learning, and administration. Each business retains its own workspace. Cross-project work receives explicit relevant dependencies rather than a copy of every workspace's context.

The owner-facing partner can coordinate across these areas. A business lead sees the relevant business context; a specialist receives the selected task context. A single-owner overview is not a grant for every worker to read every area. Workspace navigation and Telegram topics do not enforce data permissions by themselves.

Hermes remains the authority for task execution, attempts, and handoffs. Mission Control projects that recorded state; Open Brain stores selected durable knowledge and learning. Carry the originating workspace, project, and reporting destination into delegated work. Do not build another queue or infer Telegram delivery from a board update. Verify background-job reporting separately from interactive chat progress.

## Handoff

Pass the outcome, selected facts and source dates, relevant preferences, authorized repositories, acceptance criteria, excluded context, allowed effects, and return topic. Do not forward the owner's entire conversation, personal memory files, credentials, or another specialist's hidden reasoning. A deadline may be shared without the private circumstances behind it.

If a dependency is missing, request or retrieve the narrow additional source within authority. Do not silently load the global brain or treat repository boundaries as a ban on necessary cross-project work.

## Runtime alignment

1. Inventory actual profiles, personas, installed skills, memory providers, tokens, enabled platforms, and active services without printing secrets.
2. Preserve existing history and back up configuration before migration. Never copy personal bootstrap memory into specialist profiles; disable inappropriate inherited context without deleting the owner's originals.
3. Use supported profile/session routing. One inbound consumer owns each messaging token. A role in a desktop list is not automatically a separate messaging bot account.
4. Bind routes to the verified chat AND topic; retain approval-sensitive lanes. Unknown contexts must not broaden access by guessing a business or recipient.
5. Enforce the available tool and provider restrictions. Label prompt-only restrictions honestly; shared unrestricted filesystem or process-global tool access is not hard tenant isolation.
6. Preserve owner-customized persona and routing configuration when installers refresh generic defaults. Keep account mappings outside the portable suite.
7. Verify routing, scoped context, and delivery before calling a role online. Configuration validity or outbound delivery alone does not prove inbound conversation routing.

## Progress and results

Report useful progress in the originating role/topic: starting work, a meaningful finding or milestone, a blocker requiring action, and the verified result. Keep intermediate updates quiet where the platform supports it; do not send tool-by-tool noise, raw commands, secrets, or implementation plumbing. Do not claim percentages without a measurable denominator.

Delegated jobs carry an explicit return destination and report through the runtime's supported delivery mechanism. Owner-facing reporting does not authorize client/prospect messages. Preserve failed delivery for retry independently from completed work so a notification failure cannot rerun the job.

## Shared learning

Store compact, source-linked lessons and decisions in the appropriate memory scope. Preserve date, project, confidence, and evidence-versus-instruction status. Personal facts remain personal unless the owner intentionally shares a relevant subset. Keep transcripts in their session store, operational records in their authoritative system, and reusable procedures in their canonical skills.

Codex, Claude Code, and the conversational partner may share authorized cross-project knowledge while using different task contexts. Connect each through the same scope and provenance rules; a broad thought search does not automatically carry governed recall permissions.

## Acceptance cases

- An owner-wide conversation can retrieve relevant context from two authorized projects.
- A client builder starts without unrelated personal bootstrap memory or inherited chat history.
- A runtime integration task can follow a dependency into the memory or skills repository.
- Two topics select different profiles and retain their own result destinations.
- One token has one inbound consumer; restarting does not duplicate topics or overwrite customized personas.
- Progress reaches the correct topic; missing routing fails explicitly rather than sending private detail to a general channel.
- A lesson written through one authorized assistant can be recalled by another with its original scope and trust status intact.
