# Exponential Opportunity Routing

## First Question

What is supposed to compound?

Accept concrete answers such as:

- Each completed case creates reusable evals or decision precedent.
- Each participant makes matching, discovery, trust, or outcomes better for others.
- Each workflow run improves routing, thresholds, templates, or policies through measured corrections.
- Captured proprietary context makes later work faster, safer, or more accurate.
- Reusable agent or automation capabilities reduce the marginal cost of the next workflow.

Reject vague answers such as "AI", "data", "community", "scale", or "10x" without a causal loop and observable outcome.

## Routing Matrix

| Evidence | Classification | Action |
|---|---|---|
| One-off or exact local feature; no learning, network, reuse, or coordination loop | `no_fit` | Use ordinary lean/standard architecture and stay silent about ExO |
| Plausible compounding mechanism but frequency, economics, data, or authority is unknown | `leverage_candidate` | Ask only the one question that changes strategy; otherwise record as watch/proposed |
| Repeated measurable workflow, feedback signal, bounded action, and safe proof path | `intelligence_loop_candidate` | Design one workflow-level PURPOSE-to-LEARN loop with GOVERN/ASSURE |
| Existing operating model creates the bottleneck; multiple workflows and decision rights must change; sponsor and migration scope exist | `rewrite_candidate` | Backcast, assess, extract, strip, prove, then rewire proportionally |

## Proactive Suggestion Threshold

During ordinary software work, surface a candidate only when:

1. A primary signal is visible in code, workflow description, traces, or repeated user behavior.
2. The mechanism could materially change architecture or save meaningful coordination, error, or learning cost.
3. A success signal exists or one focused question can establish it.
4. The suggestion is not already dismissed or duplicative.

Do not interrupt for generic possibilities such as "add AI", "build a community", "collect more data", or "make this autonomous".

## Cross-Skill Routing

| Need | Skill |
|---|---|
| Clarify actor, outcome, evidence, prohibited consequence, stage, and risk | `software-steward` intent and situation kernel |
| Decide whether and what to automate; assign deterministic/model/agent/human methods | `workflow-automation-architect` |
| Decide loop, task graph, durable graph, or knowledge graph | `graph-engineering` |
| Shape the north-star loop and avoid early bloat | `lean-product-architect` |
| Design boundaries and architecture after intent and strategy are known | `senior-architect` |
| Permissions, data, consequential actions, external agents, or autonomy | `security-data-safety` |
| Prove the workflow is real and not a dashboard, canvas, or demo | `no-theater-software` and `evidence-before-completion` |

## Common False Positives

- More users without a participant-to-participant or learning effect.
- Storing logs without a consumer, evaluation loop, or retention policy.
- A model call that never learns from corrections.
- Multiple agents that imitate departments but do not reduce coordination.
- A dashboard showing "readiness" without changing a workflow.
- A broad MTP that cannot resolve what not to build.
- Faster task execution while approvals and waiting still dominate cycle time.
- Vendor lock-in relabeled as a value moat.
